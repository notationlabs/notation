# Workers

`@notation/cloudflare/workers` declares Cloudflare Workers and Durable Object namespaces. A Worker is declared with `$worker` in a runtime module, next to its code, and Notation builds the code for workerd. Code built outside Notation, or generated by a library, is declared with [`worker()`](#workerconfig-1).

## `$worker(config)`

A [runtime module](../../manual/file-conventions.md#runtime-modules) calls `$worker` to declare the Worker that it deploys as. The module has a default export, written with Cloudflare's own API:

```ts [runtime/api.ts]
import { $worker, type WorkerHandler } from "@notation/cloudflare/workers";

export const worker = $worker({
  id: "api",
  compatibilityDate: "2026-10-12",
  bindings: () => ({ GREETING: "hello" }),
});

export default {
  async fetch(request, env) {
    return new Response(
      `${env.GREETING} from ${new URL(request.url).pathname}`,
    );
  },
} satisfies WorkerHandler<typeof worker>;
```

When infra has finished loading, the declaration adds a Worker group with:

- the **Worker script** `api`, which uploads the bundle `dist/runtime/api/index.mjs`. Deploy names it `<app>--<stage>--api-<instance>` when it creates it. See [Names](#names).
- the **workers.dev route** of the Worker, unless `url` is `false`.

The declaration adds the Worker even when nothing imports it.

| Option               | Description                                                                                                                                              |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                 | Keys the Worker in state, and is the base of its name. Use 1 to 63 lowercase letters, digits or hyphens. Changing the id replaces the Worker.            |
| `bindings`           | A function that returns the values that the code reads from `env`, by name. See [Bindings](#bindings).                                                   |
| `compatibilityDate`  | Required. The Worker's compatibility date, such as `"2026-10-12"`. Cloudflare runs the Worker with the behaviour of the runtime on that date.            |
| `compatibilityFlags` | The Worker's compatibility flags. `nodejs_compat` is always added, as the build imports Node's built-in modules as `node:` modules, which need the flag. |
| `url`                | Serves the Worker on `https://<name>.<account subdomain>.workers.dev`, where `<name>` is the Worker's name. Defaults to `true`, as in wrangler.          |
| `entrypoint`         | The class that the module exports as its default, such as `class Api extends WorkerEntrypoint`. A Worker that binds this Worker can call its methods with types. See [RPC](#rpc). |

### Names

Deploy generates a Worker's name when it creates the Worker: `<app>--<stage>--<id>-<instance>`, where the instance is 8 random hex characters. A Worker `orders` in the `prod` stage of the `shop` app is named, for example, `shop--prod--orders-3f9a1c2e`. The name can't be set in config.

- **The longest name is 54 characters.** A Worker's name is the first label of its workers.dev URL, and a DNS label holds 63 characters. A preview URL puts a version prefix of 8 characters and a hyphen in the same label. Cloudflare refuses to serve a Worker with a longer name on workers.dev while its preview URLs are on, and turning on workers.dev turns them on. When the name would be longer, the part before the instance is cut short.
- **The name is not known before the first deploy.** Plan shows the name of a Worker that deploy creates as unknown, and so its workers.dev URL. Anything outside Notation that needs the URL must read it after the first deploy.
- **The name does not change after that.** Deploy keeps the name in the Worker's state record, and uses it on each later deploy. Only a replace changes it. The only change of params that replaces a Worker, a change of the account, fails at plan. A replace that `notation deploy --replace` asks for creates the new Worker with a new name, and then deletes the old one.
- **Deploy fills in the name wherever the Worker is bound.** A service binding to the Worker, a Durable Object binding to a namespace that it hosts, and a binding of the Worker to itself all hold the generated name. A Worker that binds itself is created once, with the binding.
- **A new Worker with the id of an old one is a second Worker.** This happens when the state record of a Worker is lost. The old Worker stays in the account.

### Bindings

`bindings` returns an object literal with no spread or computed keys. The runtime build keeps the names and removes the values. Each value is bound by its type:

| Value                                                               | Binding                  | Type in `env`                                                                         |
| ------------------------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------- |
| A namespace from [`$durableObject`](#durableobjectconfig)           | Durable Object namespace | `DurableObjectNamespace<Class>`                                                       |
| A Worker from `$worker` or `worker()`                              | Service binding          | `Service<Class>` for a Worker with an [`entrypoint`](#rpc) class, otherwise `Fetcher` |
| A [`SecretsStoreSecret`](secrets.md) resource                       | Secrets Store secret     | `SecretsStoreSecret`                                                                  |
| A [credential](#worker-secrets), such as `apiKey.credentials.value` | Secret text              | `string`                                                                              |
| An `R2Bucket` resource                                              | R2 bucket                | `R2Bucket`                                                                            |
| A [`KVNamespace`](kv.md) resource                                   | KV namespace             | `KVNamespace`                                                                         |
| A value from `json(value)`                                          | JSON                     | the type of `value`                                                                   |
| A string, or an output ref or a derived value of one                | Plain text               | `string`                                                                              |

`WorkerEnv<typeof worker>` is the type of `env`, and `WorkerHandler<typeof worker>` is the type of the default export. A Worker is uploaded after each Worker, R2 bucket, KV namespace and store secret that it binds, and after each resource whose credential or output ref it binds. See [Output refs](../../reference/resource.md#output-refs) for refs and derived values such as `` text`${api.url}/callback` ``.

An infra module declares the R2 bucket, the KV namespace and the source of a Worker secret, and the runtime module imports them. `R2Bucket` and `KVNamespace` are resources from `@notation/cloudflare/resources`, and `sources.Env` is from `@notation/std/resources`:

::code-group

```ts [infra/main.ts]
import { kv, r2 } from "@notation/cloudflare/resources";
import { sources } from "@notation/std/resources";

export const uploads = new r2.R2Bucket("uploads", {
  config: {
    BucketName: "shop-uploads",
    Jurisdiction: "default",
    StorageClass: "Standard",
  },
});

export const cache = new kv.KVNamespace("cache", {
  config: { Title: "shop-cache" },
});

export const apiKey = new sources.Env("api-key", {
  config: { key: "API_KEY" },
});
```

```ts [runtime/api.ts]
import {
  $worker,
  json,
  type WorkerHandler,
} from "@notation/cloudflare/workers";
import { apiKey, cache, uploads } from "../infra/main";

export const worker = $worker({
  id: "api",
  compatibilityDate: "2026-10-12",
  bindings: () => ({
    UPLOADS: uploads,
    CACHE: cache,
    CONFIG: json({ retries: 3 }),
    API_KEY: apiKey.credentials.value,
  }),
});

export default {
  async fetch(request, env) {
    await env.CACHE.put("last", new Date().toISOString());
    const object = await env.UPLOADS.get("logo.png");
    return new Response(object?.body ?? null, {
      headers: { "x-retries": String(env.CONFIG.retries) },
    });
  },
} satisfies WorkerHandler<typeof worker>;
```

::

- A binding to a bucket in a jurisdiction other than `default` names the jurisdiction.
- `json(value)` takes a JSON value. Deploy stores the value in state, and plan shows it. Bind a secret as a [credential](#worker-secrets) instead.

Two Workers can bind each other as services. Each service binding is a [contribution](../../reference/resource.md#cycles) to the Worker's script, so deploy can break the cycle:

1. Deploy uploads one of the Workers without its service bindings.
2. It uploads the other Worker, which binds the first.
3. It uploads the first Worker again, with its service bindings.

Between steps 1 and 3, the first Worker's `env` has no service bindings, so a request that calls the other Worker fails.

TypeScript can't type two Workers that bind each other through `bindings`, or a Worker that binds itself. The type of each Worker depends on the type of the other, and TypeScript types both as `any`, which fails under `strict`. To keep one direction typed, bind the other direction with [`addBindings()`](#addbindingsworker-bindings).

### RPC

When a Worker's default export is a `WorkerEntrypoint` class, a Worker that binds it can call the class's methods over RPC. Pass the class as `entrypoint`, and the binding is typed `Service<Class>` in `env`:

::code-group

```ts [runtime/github.ts]
import { WorkerEntrypoint } from "cloudflare:workers";
import { $worker, type WorkerEnv } from "@notation/cloudflare/workers";

export type Input = { headers: Record<string, string>; body: string };

export default class Github extends WorkerEntrypoint<WorkerEnv<typeof github>> {
  async receive(input: Input) {
    const key = await this.env.ROOT_KEY.get();
    // verify the signature, parse the event …
    return { received: true };
  }
}

export const github = $worker({
  id: "github",
  compatibilityDate: "2026-10-12",
  bindings: () => ({ ROOT_KEY: rootKey }),
  entrypoint: Github,
  url: false,
});
```

```ts [runtime/router.ts]
import { $worker, type WorkerHandler } from "@notation/cloudflare/workers";
import { github, type Input } from "./github";

export const router = $worker({
  id: "router",
  compatibilityDate: "2026-10-12",
  bindings: () => ({ GITHUB: github }),
});

export default {
  async fetch(request, env) {
    const input: Input = {
      headers: Object.fromEntries(request.headers),
      body: await request.text(),
    };
    return Response.json(await env.GITHUB.receive(input));
  },
} satisfies WorkerHandler<typeof router>;
```

::

`env.GITHUB.receive(input)` is typed. An unknown method, or an argument of the wrong type, is a type error. The router's runtime bundle doesn't include the GitHub Worker's code: the build removes the values of `bindings`, and then the import of `github` is unused.

Deploy doesn't read `entrypoint`. The infra build replaces it with a function that throws, so it never loads the class or `cloudflare:workers`. The service binding has no `entrypoint` field, so Cloudflare sends the calls to the default export.

Set `url: false` when the class has no `fetch` method. The Worker then has no workers.dev URL, and only the Workers that bind it can call it.

The build fails when `entrypoint` is not the class that the module exports as its default:

```text
runtime/github.ts:17:15: entrypoint must name the class that github.ts declares and exports as its default. Pass entrypoint: Github.
```

- The class must have a name, and be declared before `$worker`. The build fails for a class declared after it, as the Worker would read the class before its declaration runs, and throw at start:

  ```text
  runtime/github.ts:5:15: entrypoint is Github, which github.ts declares after $worker. Declare the class before $worker.
  ```

- The class must be declared in the Worker's module, as `export default class Github`, or as `class Github` with `export default Github` or `export { Github as default }`. The build doesn't follow imports or re-exports, so a class that the module imports, or a default export that it re-exports from another module, fails the build.
- Only the default export can be bound. Cloudflare can also bind a named entrypoint, such as `export class Admin extends WorkerEntrypoint`, but `$worker` doesn't support it.
- A class that is not a `WorkerEntrypoint`, such as a Durable Object class, type-checks as `entrypoint`. A Worker that binds it gets a `Fetcher`.
- TypeScript doesn't check that the arguments and the return values of the methods can be sent over RPC. A method that takes a function or a class instance type-checks, and fails at runtime.

### Worker secrets

A Worker secret is stored with the Worker, not in a Secrets Store. In the handler, the binding is a string. To declare one, bind a [credential](../../manual/secrets.md#credentials), such as the value of a source or of a token:

```ts [runtime/api.ts]
export const worker = $worker({
  id: "api",
  compatibilityDate: "2026-10-12",
  bindings: () => ({ API_KEY: apiKey.credentials.value }),
});
```

A credential is typed `CredentialRef<string>`, so TypeScript tells it from plain text. A credential becomes a secret, and an output ref to any other output becomes plain text.

The Worker script holds its secrets in its `Secrets` param, which maps each binding name to a credential. State holds a marker for each name, with the credential's version, and never the value:

```ts
Secrets: {
  API_KEY: { $credential: { resource: "api-key", name: "value", version: "7b1e52c0…" } },
}
```

Deploy sends the values in the upload of the Worker's code, as `secret_text` bindings. So one request sets the code and its secrets, and the code never runs without them. A failed upload changes neither.

- **A create sends every secret.** Deploy gets the value of each credential, from memory, from the source, or by rolling a token.
- **An update sends only the secrets whose credential has a new version.** Cloudflare keeps a secret that an upload leaves out, so the other secrets keep their values, and deploy does not need them.
- **A new version uploads the Worker again.** An `Env` or a `Dotenv` without `track` has a new version on every deploy, so a Worker that binds its value is uploaded on every deploy. See [When a value is written](../../manual/secrets.md#when-a-value-is-written).
- An upload keeps a secret that Notation did not send, such as one set with `wrangler secret put`. A binding in `bindings` with the name of such a secret replaces it.
- A value changed in the dashboard or with wrangler stays until deploy next sends the secret.
- A secret deleted in the dashboard or with wrangler shows as drift. The next `notation deploy` uploads the Worker, and sends that secret again.

When a Worker stops binding a secret, deploy deletes the secret from the Worker after the upload of the new code. Cloudflare keeps a secret that an upload leaves out, so the delete is a separate request. When the Worker is removed, deploy deletes the Worker, which deletes its secrets with it.

When a Worker's `id` changes, the Worker gets a new name. Deploy uploads the new Worker with all its secrets, and then deletes the old Worker.

As an alternative, a Worker can bind a [Secrets Store secret](secrets.md). That secret belongs to the account, and several Workers can share it.

### Gradual rollouts

Cloudflare deploys each upload of a Worker to all traffic, so an upload during a [gradual deployment](https://developers.cloudflare.com/workers/configuration/versions-and-deployments/gradual-deployments/) ends it. Before each upload to a Worker that exists, deploy reads the Worker's deployments. When the latest deployment splits traffic between more than one version, deploy fails before the upload:

```text
The Worker shop--prod--api-3f9a1c2e is in a gradual rollout: 50% on version 3c9e…, 50% on version 81fa…. An upload would end the rollout. Finish or cancel it in Cloudflare, then deploy again.
```

The check applies to any upload: a change of code, of bindings, or of a secret. Deploy reads the deployments and then uploads, and Cloudflare has no request that does both. So a rollout that starts between the two requests is ended by the upload.

A Worker that binds the value of an `Env` or a `Dotenv` without `track` is uploaded on every deploy, because the version of the value changes on every deploy. So while that Worker is in a rollout, every deploy of the stage fails. Set [`track`](../../manual/secrets.md#tracking-a-value) on the source, so that the Worker is uploaded only when the value changes.

### Deleting a Worker that other Workers bind

Cloudflare doesn't delete a Worker that another Worker binds as a service, or whose Durable Object namespace another Worker binds, unless the delete is forced. Deploy deletes a Worker when its `id` changes, when it is removed from code, and in destroy.

- When every Worker that binds it is in the same app and stage, the delete is forced.
- When another Worker binds it, such as a Worker of another app or stage, or one that Notation did not deploy, the delete fails, and the error names that Worker. A Pages project that binds the Worker, and a Worker that sends it tail events, stop the delete in the same way. Remove the reference first.

Deleting a Worker deletes the objects of the Durable Object namespaces that it hosts, forced or not.

Namespaces can't close a cycle. When two Workers each bind a namespace that the other hosts, plan fails, as each Worker is uploaded after the host of each namespace that it binds.

## `worker(config)`

`worker()` declares a Worker from a prebuilt JavaScript module or a [bundle](../../reference/bundle.md). It takes the options of [`$worker`](#workerconfig), plus `code`.

To deploy code built outside Notation, pass a file:

```ts [infra/worker.ts]
import { worker } from "@notation/cloudflare/workers";

export const external = worker({
  id: "external",
  code: { type: "file", path: "external/worker.mjs" },
  compatibilityDate: "2026-10-12",
});
```

The path can be absolute or relative to the project root. **Notation uploads the file as-is:** it doesn't bundle imports or compile TypeScript. Build the module before running plan or deploy. The Worker tracks the file, so a change to its contents plans an upload.

`worker()` reads the file's exports without executing it. A Durable Object namespace that the Worker binds is hosted on it when the file exports the namespace's class by name. A class re-exported with `export *` is not found, as for a bundle.

### A bundle as the code

A library can pass a bundle that deploy builds, such as a router that generates a Worker from a route table:

```ts [node_modules/acme-router/index.js]
import { fileURLToPath } from "node:url";
import { bundle } from "@notation/build/resources";
import { worker } from "@notation/cloudflare/workers";

export function router({ id, routes, bindings }) {
  const code = bundle({
    id,
    platform: "workerd",
    entry: fileURLToPath(new URL("./template.js", import.meta.url)),
    modules: {
      "virtual:routes": `export default ${JSON.stringify(routes)};`,
    },
  });
  return worker({ id, code, compatibilityDate: "2026-10-12", bindings });
}
```

The bundle must have `platform: "workerd"`. `worker()` fails for a bundle built for `node`. Its `entrypoint` takes a marker from `entrypointType()` instead of the class. See [RPC to a `worker()`](#rpc-to-a-worker).

- **The Worker is the same as one from `$worker`.** It has the same resource ids, so a `$worker` with the id `router` and a `worker({ id: "router" })` fail with `Duplicate Worker id "router"`. Its group uploads the bundle's `index.mjs`.
- **The bundle is not in the Worker's group.** The script depends on the bundle, so deploy writes the bundle before it uploads the script.
- **It binds every value that `$worker` binds**, and another Worker can bind it as a service.
- **It hosts a Durable Object namespace that it binds when the bundle's entry exports the namespace's class by name.** `bundle()` reads the exports of the entry when it is called. A class that the entry re-exports with `export *` is not found, and plan fails. A container of the namespace runs on the Worker, as for a `$worker`.

A `$worker` that is replaced by a `worker()` with the same id and the same exports keeps its namespaces on the same script.

### RPC to a `worker()`

A package that ships a Worker declares it with `worker()`, as the infra build doesn't strip a `$worker` in `node_modules`. The package's infra code can't load the Worker's class, because the class imports `cloudflare:workers`. So it imports the class as a type, and passes `entrypointType<typeof Class>()` as `entrypoint`:

::code-group

```ts [@acme/github: infra/github.ts]
import { bundle } from "@notation/build/resources";
import { entrypointType, worker } from "@notation/cloudflare/workers";
import type Github from "../worker/github";

export const github = worker({
  id: "github",
  code: bundle({ id: "github", platform: "workerd", entry: githubEntry }),
  compatibilityDate: "2026-10-12",
  bindings: () => ({ ROOT_KEY: rootKey }),
  entrypoint: entrypointType<typeof Github>(),
  url: false,
});
```

```ts [@acme/github: worker/github.ts]
import { WorkerEntrypoint } from "cloudflare:workers";
import type { WorkerEnv } from "@notation/cloudflare/workers";
import type { github } from "../infra/github";

export type Input = { headers: Record<string, string>; body: string };

export default class Github extends WorkerEntrypoint<WorkerEnv<typeof github>> {
  async receive(input: Input) {
    const key = await this.env.ROOT_KEY.get();
    // verify the signature, parse the event …
    return { received: true };
  }
}
```

::

A Worker that binds `github` gets `Service<Github>` in `env`, as for a `$worker` with an [`entrypoint`](#rpc). `this.env` inside the class is typed too.

`entrypointType()` returns an object that exists only for its type. Deploy ignores it. The build doesn't check that the marker names the bundle's default export, as the marker has no class to compare with the export. A marker for a class that the bundle doesn't export as its default types the Worker's callers wrongly.

## `addBindings(worker, bindings)`

`addBindings()` adds bindings to a Worker from other infra code, such as a library that adds a feature to a Worker that it didn't declare:

```ts [infra/main.ts]
import { addBindings } from "@notation/cloudflare/workers";
import { github } from "../runtime/github";
import { router } from "../runtime/router";

addBindings(router, { CHANNEL_GITHUB: github });
```

It takes a Worker from `$worker` or `worker()`, and an object of bindings. The values are the ones that `bindings` accepts. The Worker resolves them together with its own bindings, so each is uploaded, and orders the deploy, as if `bindings` had returned it.

`WorkerEnv<typeof router>` doesn't include the bindings from `addBindings()`, as they depend on which infra code runs. The Worker reads such a binding by its name, and types it from a contract that it shares with the code that called `addBindings()`. `WorkerEnv` has no index signature, so widen `env` before indexing it with a computed name:

```ts [runtime/router.ts]
const name = `CHANNEL_${provider.toUpperCase()}`;
const channel = (env as Record<string, unknown>)[name] as Service<Channel>;
const received = await channel.receive(input);
```

- A Worker hosts a Durable Object namespace only when its own module, the entry of its bundle, or its code file exports the namespace's class. So a namespace from `addBindings()` works only when another Worker hosts it.
- Two Workers that bind each other through `addBindings()` deploy, in the same way as two Workers that bind each other through `bindings`.
- Call `addBindings()` from an infra module. The build fails for a Worker whose code calls it, as it only runs at deploy. This includes a call at the top level of a `$worker` module: the infra build keeps only the declaration of that module, so the call would not run at deploy, and its bindings would not be uploaded.

`addBindings()` fails when:

1. A name is bound twice, by `bindings` and `addBindings()`, or by two calls to `addBindings()`. A clash between two calls fails at the second call. A clash with `bindings` fails when the Worker reads its bindings, once the infra modules have loaded. Both errors name the location of the call to `addBindings()`. The error for two calls also names the location of the earlier call:

   ```text
   addBindings() at infra/main.ts:5 binds CHANNEL_GITHUB on $worker({ id: "router" }) in runtime/router.ts, which already binds CHANNEL_GITHUB in its bindings. Give one of the bindings another name.
   ```

2. It is called from an `onEvaluationEnd` callback. The Workers read their bindings once the infra modules have loaded, so `addBindings()` must be called while they load, such as in the function that declares what it binds. Only engine and package code registers such callbacks, so the error names the location of the call, which points at the package to fix.
3. The first argument isn't a Worker from `$worker` or `worker()`.
4. It is called while no resource graph is being collected, or with a Worker that was declared in another resource graph, such as one collected earlier by the same process.

## `$durableObject(config)`

A runtime module calls `$durableObject` to declare a Durable Object namespace. The module holds only this declaration and the class. A Worker hosts the namespace when it binds the namespace and its module exports the class:

::code-group

```ts [runtime/counter.ts]
import { DurableObject } from "cloudflare:workers";
import { $durableObject } from "@notation/cloudflare/workers";

export class Counter extends DurableObject {
  async increment() {
    const count = ((await this.ctx.storage.get<number>("count")) ?? 0) + 1;
    await this.ctx.storage.put("count", count);
    return count;
  }
}

export const counters = $durableObject({ id: "counters", class: Counter });
```

```ts [runtime/api.ts]
import { $worker, type WorkerHandler } from "@notation/cloudflare/workers";
import { counters } from "./counter";
export { Counter } from "./counter";

export const worker = $worker({
  id: "api",
  compatibilityDate: "2026-10-12",
  bindings: () => ({ COUNTERS: counters }),
});

export default {
  async fetch(request, env) {
    const count = await env.COUNTERS.getByName("one").increment();
    return new Response(`count=${count}`);
  },
} satisfies WorkerHandler<typeof worker>;
```

::

| Option      | Description                                                                                                                                                                                                                     |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`        | Keys the namespace. Use 1 to 64 letters, digits, hyphens or underscores. It can't change while the namespace exists: see [Renaming, moving and deleting](#renaming-moving-and-deleting).                                        |
| `class`     | The namespace's class, by name, such as `class: Counter`. Cloudflare finds the class by its export name, so the hosting Worker exports the class under the name written here.                                                   |
| `protect`   | Defaults to `true`. Plan fails for a change that would delete a protected namespace. Plan reads the value from state, so `protect: false` takes effect after it is deployed. See [Deleting a namespace](#deleting-a-namespace). |
| `container` | Runs a container for each object. Deploy builds the image and creates a container application for the namespace. See [Containers](#containers).                                                                                 |

The infra build doesn't load the class, or its imports such as `cloudflare:workers`. It replaces the class with a function of the same name.

### Hosting

Exactly one of the Workers that bind a namespace exports its class, and that Worker hosts the namespace. Every other Worker that binds the namespace binds it on the hosting Worker, and is uploaded after it. Plan fails when:

- no Worker that binds the namespace exports the class. The error names the Worker's module, or the entry of a [`worker()`](#workerconfig-1). A class re-exported with `export * from` is not found, because the names that `export *` brings in are not known when the bindings are resolved.
- two Workers that bind the namespace export the class.
- one Worker hosts two namespaces with the same class.

The host is found by the export's name only. A Worker that binds the namespace and exports a different class under the same name, such as another `Counter`, is taken as the host.

### Renaming, moving and deleting

A new namespace uses SQLite storage. Deploy uploads Cloudflare's declarative `exports` map of the hosting Worker, with each namespace that the Worker hosted before. Cloudflare keys a namespace by its Worker and its class name, and deleting a namespace deletes all its objects, which can't be undone. So plan and deploy fail, before deploy changes anything, for a change that would delete a namespace that is protected in state:

- When a namespace's `class` changes and its `id` stays the same, deploy renames the class, and the namespace keeps its objects.
- A namespace's `id` can't change. Plan fails, and says to change the id back. When the `class` changes too, plan can't pair the old and new namespaces, so it fails with the message for a deleted namespace, which also says to change the id back if it changed.
- When the hosting Worker no longer hosts a namespace, plan fails, unless the namespace is unprotected in state. See [Deleting a namespace](#deleting-a-namespace).
- When a namespace's class export moves to another Worker, and the old host still binds the namespace, deploy moves the namespace and its objects to the new host. See [Moving a namespace](#moving-a-namespace). When the old host no longer binds the namespace, plan fails, unless the namespace is unprotected in state.
- When a Worker is removed, as when its `id` changes, deploy deletes all its namespaces. Plan fails unless each of them is unprotected in state.
- Plan fails if a namespace takes a class that another namespace had on the same Worker before, as the new namespace would get the old one's objects. Rename or delete the old namespace in one deploy, and give its class to the new namespace in a later deploy.

`notation destroy` doesn't make these checks. It deletes each Worker with its namespaces.

### Moving a namespace

To move a namespace to another Worker, export its class from the new host's module, and stop exporting it from the old host's module. Keep binding the namespace from the old host in the same deploy:

::code-group

```ts [runtime/web.ts]
import { $worker, type WorkerHandler } from "@notation/cloudflare/workers";
import { rooms } from "./rooms";
// No longer exports Room.

export const worker = $worker({
  id: "web",
  compatibilityDate: "2026-10-12",
  bindings: () => ({ ROOMS: rooms }),
});

export default {
  async fetch(request, env) {
    return new Response(env.ROOMS.idFromName("lobby").toString());
  },
} satisfies WorkerHandler<typeof worker>;
```

```ts [runtime/api.ts]
import { $worker, type WorkerHandler } from "@notation/cloudflare/workers";
import { rooms } from "./rooms";
export { Room } from "./rooms";

export const worker = $worker({
  id: "api",
  compatibilityDate: "2026-10-12",
  bindings: () => ({ ROOMS: rooms }),
});

export default {
  async fetch(request, env) {
    return new Response(env.ROOMS.idFromName("lobby").toString());
  },
} satisfies WorkerHandler<typeof worker>;
```

::

The old host now binds the namespace on the new host, so deploy uploads the new host first. That upload moves the namespace in three steps:

1. Deploy uploads the new host with the class expecting the namespace, and without its binding to the namespace.
2. Deploy sets the class as transferred on the old host. Cloudflare moves the namespace, with its objects.
3. Deploy uploads the new host again, with the binding.

Then deploy uploads the old host, with its binding on the new host. A later deploy can remove that binding.

Between steps 1 and 3, the new host's `env` has no binding to the namespace, so a request on the new host that uses it fails. From step 2 until deploy uploads the old host, the old host's deployed version still binds the class as its own, so a request on the old host that uses it fails too. If step 2 fails, the namespace and its objects stay on the old host, and the new host's class waits for them. The next deploy runs the move again.

To find the old host, deploy lists the account's namespaces when a Worker hosts a namespace that is new to it, and another Worker binds that namespace. The new host reads the names of the Workers that bind the namespace from their state records at the start of the deploy, as those Workers depend on it. If one of those Workers hosts a namespace with the same class, deploy moves it. If none does, the namespace is new. A Worker that this deploy creates has no record, and has never hosted the namespace, so it is left out.

When a Worker that binds the namespace has no state record, deploy also checks that no Worker in the account with a name that deploy gives that Worker hosts the class. Such a Worker may be the old host, with its state record lost. Without the check, the new host would start an empty namespace while the old Worker keeps the objects. The names are `<app>--<stage>--<id>-` followed by 8 hex characters, cut as deploy cuts a long name. When such a Worker hosts the class, deploy fails and names it. The check never moves a namespace. It can fail a deploy that is correct: a Worker whose id ends in something that looks like an instance, such as `orders-deadbeef`, has a name that matches `orders`. Two Workers whose long names are cut to the same part match each other. Two Workers whose ids differ only in runs of hyphens, such as `a--b` and `a-b`, also match each other, as deploy puts one hyphen in a generated name for each run.

Plan fails when:

- the namespace's `class` also changes. Move the namespace first, and change the class in a later deploy.
- the namespace that moves has the class of another namespace that the old host had before. The moved namespace would get that namespace's objects.
- the old host no longer binds the namespace, and the namespace is protected in state. Without the binding, deploy doesn't know where the namespace moves to, and the old host's upload would delete it.
- the new host gets a namespace that another Worker binds, and the same deploy renames or deletes another namespace of the new host. The first upload of a move would apply the rename or delete before the move is done. Plan can't tell whether the namespace moves or is new, so it fails in both cases. Make the two changes in separate deploys.

Deploy fails, before it uploads the new host, when this deploy creates the new host, and when the check above finds a Worker with no state record. Plan doesn't catch this, as plan doesn't list the account's namespaces. Deploy the new host without the namespace first. Deploy also fails when the old host hosts a namespace with key-value storage, which Notation doesn't support, or a namespace that Cloudflare's list doesn't show as SQLite.

If a move stops part way through, the next deploy finishes it. The new host's state is updated only after the last upload, so the next deploy runs the move again. It finds the namespace on the old host, or on the new host if Cloudflare already moved it.

### Deleting a namespace

Deleting a namespace takes two deploys. First set `protect: false` on its declaration, and deploy while the Worker still hosts the namespace:

```ts [runtime/rooms.ts]
export const rooms = $durableObject({
  id: "rooms",
  class: Room,
  protect: false,
});
```

This deploy saves the value in the state of the hosting Worker. Plan lists the Worker as an update, and deploy uploads it again, without changing the namespace.

In a later deploy, remove the declaration, its binding and its class. Deploy uploads a `deleted` entry for the namespace's class. The Worker's module must no longer export the class, or Cloudflare rejects the upload. In the same way, a later deploy can remove the hosting Worker, or change its `id`, once all its namespaces are unprotected in state.

Plan reads `protect` from state, not from code. A deploy that sets `protect: false` and also stops hosting the namespace fails at plan.

### Containers

A namespace can run [Cloudflare Containers](https://developers.cloudflare.com/containers/): each object can start a container and send it requests. Set `container` to the image and the size of the containers:

```ts [runtime/sandbox.ts]
import { DurableObject } from "cloudflare:workers";
import { $durableObject } from "@notation/cloudflare/workers";

export class Sandbox extends DurableObject {
  async fetch(request: Request) {
    const container = this.ctx.container!;
    if (!container.running) container.start();
    return await container.getTcpPort(8080).fetch(request);
  }
}

export const sandboxes = $durableObject({
  id: "sandboxes",
  class: Sandbox,
  container: {
    image: { context: "containers/sandbox" },
    maxInstances: 5,
    instanceType: "basic",
  },
});
```

For a namespace with `container`, deploy:

1. Builds the image with Docker and pushes it to the account's Cloudflare registry, as a `ContainerImage` does. See [ContainerImage](containers.md#containerimage).
2. Uploads the hosting Worker, with the class in the upload's `containers` list.
3. Creates a container application for the namespace, with the image pinned by its digest. A later change to the image or to the size starts a rollout.

| Option                 | Description                                                                                                                                                                                                                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `image.context`        | Required. The build context directory, relative to the project root.                                                                                                                                                                                                                     |
| `image.dockerfile`     | The Dockerfile, relative to the project root. Defaults to `Dockerfile` in the build context.                                                                                                                                                                                             |
| `image.buildArgs`      | Values for `docker build --build-arg`, by name. Don't put secrets here: Docker keeps the values in the image's history.                                                                                                                                                                  |
| `image.repository`     | The repository in the registry. Defaults to `<app>--<stage>--<id>`, with the namespace id in lower case, each run of other characters than letters and digits replaced by one hyphen, and no hyphen at the start or end. When no letters or digits are left, the id part is `namespace`. |
| `maxInstances`         | Required. The most containers that run at once.                                                                                                                                                                                                                                          |
| `instanceType`         | Such as `lite`, `basic` or `standard-1`. Set either `instanceType`, or `vcpu` and `memoryMib`. Without any of them, Cloudflare uses `lite`.                                                                                                                                              |
| `vcpu`, `memoryMib`    | A custom size.                                                                                                                                                                                                                                                                           |
| `diskMb`               | The disk size in MB, with `vcpu` and `memoryMib` only.                                                                                                                                                                                                                                   |
| `environmentVariables` | Variables for the container, by name. Don't put secrets here: the values are stored as plain text in state and shown in plan output.                                                                                                                                                     |
| `network`              | `mode` (`private` or `public`), `assignIpv4` and `assignIpv6` (`none` or `predefined`). Cloudflare can't change the mode of an application, so plan fails for a change to it.                                                                                                            |

The application's name is `<app>-<stage>-<id>-<hash>`. The id is put in lower case, with each run of other characters than letters and digits replaced by one hyphen, and with no hyphen at the start or end. The hash is 8 hex characters of a SHA-256 of the app, stage and id, so the name is unique for each of them. Cloudflare refuses a name that contains two consecutive hyphens, so the name can't use the `<app>--<stage>--` form of Worker names. Cloudflare also refuses a name that starts with a digit, so when the app name starts with a digit, the name starts with `c-`.

Deploy runs the `docker` CLI, so Docker must be running on the machine that deploys. See [Docker](containers.md#docker). Containers need an account on the Workers Paid plan, and the API token needs the **Containers: Edit** permission.

A namespace with `container` can move to another Worker, as in [Moving a namespace](#moving-a-namespace). The first upload of the new host sends the class in `containers`, before the namespace arrives. The namespace keeps its ID. The application is now for another Worker, so after the move, deploy deletes the application and creates it again with the same name and image. The containers stop until the new application has started them. The image is not built again.

To stop running containers, remove `container`. Deploy uploads the Worker without the class in `containers`, and then deletes the application. The namespace and its objects stay. The image stays in the registry. After this deploy, requests to the objects can time out for several minutes, and Cloudflare still sets `ctx.container` on them. No application runs containers for them, so the class must stop starting containers.

A namespace with `container` is deleted as in [Deleting a namespace](#deleting-a-namespace). Deploy uploads the Worker with the `deleted` entry, and then deletes the application.

## Credentials

Deploy reads two environment variables:

- `CLOUDFLARE_API_TOKEN`: an API token with the **Workers Scripts: Edit** permission.
- `CLOUDFLARE_ACCOUNT_ID`: the account to deploy to. It is stored in state, so a later deploy updates or deletes each Worker in the account it was made in.

A Worker can't move to another account. If `CLOUDFLARE_ACCOUNT_ID` changes, plan and deploy fail, because replacing each Worker would delete the objects of the namespaces that it hosts. To deploy to another account, first run `notation destroy` with the old account, or deploy to another stage.

A generated name ends in a random instance, so a Worker that someone else made in the account does not have it. When a create stops before deploy records it, the next deploy finds the Worker under the name in the `creating` record, and takes it over. See [Recoverable creates](../../internals/reconciler.md#recoverable-creates).
